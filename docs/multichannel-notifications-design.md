# Уведомления в Telegram, e-mail и Web Push — дизайн

## Цель

Всё, что бот Remnashop отправляет пользователю (автоматические уведомления и
ручные рассылки администратора), доходит до пользователя по всем его каналам:

| Канал | Кому | Как пользователь управляет |
|---|---|---|
| Telegram | у кого привязан Telegram | штатно в боте (как сейчас) |
| E-mail | у кого подтверждён e-mail | в профиле кабинета: «служебные» и «новости» отдельно; в каждом письме — отписка в один клик |
| Web Push | кто включил уведомления в установленном приложении (PWA) | настройками телефона/браузера; на устройстве — кнопка «отключить на этом устройстве» |

## Что считается уведомлением

`notify_user` вызывается ~240 раз, почти все — интерактивные ответы бота в
диалогах («неверное значение», «подтвердите»). Их **не** дублируем. В каналы
уходят только:

- **служебные** — события `UserEvent` (подписка скоро закончится / закончилась /
  закончилась N дней назад, исчерпан трафик, льготный период, устройство не
  подключено, блокировка торрентов), реферальные начисления, «платежи снова
  доступны»;
- **новости** — ручные рассылки администратора (`broadcast`).

Напоминание «подписка скоро закончится» по e-mail уже отправляет отдельный
надёжный конвейер (`subscription_email_reminders`, флаг
`subscription_expiration_email_enabled`). Для этого события e-mail-канал новой
схемы не используется — дублей не будет.

## Где живёт логика

Вся раздача по каналам — в **Remnashop** (там рождаются уведомления).
Clean Pay — только интерфейс пользователя: включение push на устройстве,
галочки e-mail, страница отписки.

```
событие / рассылка ─► Remnashop: UserNotificationDispatcher
                        ├─ Telegram  (как сейчас, NotificationService)
                        ├─ outbox: e-mail  ─► worker (отдельный SMTP рассылок, лимит скорости)
                        └─ outbox: push    ─► worker (pywebpush, VAPID)
Clean Pay (PWA) ──► API Remnashop: push-подписка, настройки e-mail, отписка
```

### Remnashop

- **Миграция:**
  - `users.email_service_notifications_enabled` (по умолчанию `true`);
  - `users.email_news_enabled` (по умолчанию — см. «Решения»);
  - таблица `web_push_subscriptions` (пользователь, endpoint, ключи p256dh/auth, устройство, ошибки);
  - таблица `notification_deliveries` — outbox: канал, категория, готовый текст, статус, попытки, `next_attempt_at`, ключ идемпотентности.
- **`UserNotificationDispatcher.deliver(user, payload, category)`:** Telegram — сразу, как сейчас; e-mail и push — строками в outbox. Рассылка администратора ставит в outbox всех получателей пачками.
- **Воркер outbox** (taskiq, каждую минуту): доставка с ограничением скорости, повторы с экспоненциальной паузой, ответ push 404/410 → подписка удаляется.
- **Отрисовка:**
  - Telegram-HTML → письмо: разрешённые теги, `<tg-emoji>` → обычный эмодзи, multipart text + html;
  - Telegram-HTML → push: заголовок + до ~150 символов текста;
  - кнопки-ссылки остаются ссылками, а кнопки бота («Продлить», «Купить») ведут в кабинет.
- **Письма** соответствуют требованиям Gmail / Yandex / Mail.ru для массовых отправителей:
  - `List-Unsubscribe` (HTTPS) и `List-Unsubscribe-Post: List-Unsubscribe=One-Click` (RFC 8058);
  - `List-Id`, `Message-ID` своего домена;
  - `Precedence: bulk` для новостей и `Auto-Submitted: auto-generated` для служебных;
  - видимая ссылка «Отписаться» в теле;
  - SPF / DKIM / DMARC настраиваются в DNS и у почтового провайдера (инструкция в README).
- **Отдельный SMTP для рассылок:** `BULK_EMAIL_*`, свой лимит писем в минуту. Через общий интерфейс отправителя позже подключается сервис рассылок (HTTP API) без изменения логики. Коды входа идут через основной SMTP и рассылкам не мешают.
- **Web Push:** `WEB_PUSH_VAPID_PUBLIC_KEY` / `WEB_PUSH_VAPID_PRIVATE_KEY` / `WEB_PUSH_VAPID_SUBJECT`. TTL — сутки для служебных и 3 дня для новостей. Срочность `high` для служебных.
- **API (публичный, под ключом auth-сервиса Clean Pay):**
  - `GET /api/v1/public/auth/notifications/push/key`;
  - `GET` и `POST /api/v1/public/auth/notifications/push/subscription`, `POST …/push/subscription/delete`;
  - расширение `notification-preferences` полями «служебные / новости»;
  - `POST /api/v1/public/auth/notifications/unsubscribe` — по подписанному токену, без входа.

### Clean Pay

- **Service worker:** `push` → системное уведомление с иконкой бренда; `notificationclick` → открыть или сфокусировать приложение на нужной странице.
- **Карточка «Уведомления на этом устройстве»** в кабинете и профиле:
  - Android и ПК — кнопка «Включить»;
  - iPhone вне установленного приложения — подсказка «добавьте на экран „Домой“» (iOS даёт push только приложениям с главного экрана, iOS 16.4+);
  - при отказе в разрешении — инструкция, где включить в настройках.
- **Профиль:** две галочки e-mail — «Служебные уведомления» и «Новости и рассылки». Существующая галочка «напоминания об окончании подписки» становится частью «служебных».
- **Страница `/unsubscribe`:** ссылка из письма, отписка в один клик и ссылка в профиль для повторной подписки.

## Порядок выпуска

Сначала Remnashop (миграция, API, воркер), затем Clean Pay. Clean Pay требует
минимальную ревизию Alembic новой миграции. Проверка — на тестовом стенде
(VM 110) с отдельным тестовым SMTP-ящиком рассылок.

## Решения

1. **Новости на e-mail выключены по умолчанию** и включаются только явным
   согласием пользователя (ст. 18 закона «О рекламе»):
   - при регистрации в Clean Pay — отдельная галочка «Хочу получать новости
     и рассылки на e-mail», по умолчанию снята; согласие уходит в Remnashop
     вместе с регистрацией и сохраняется с отметкой времени;
   - позже — галочкой в профиле.
   **Служебные уведомления включены у всех изначально** (миграция ставит
   `true` всем существующим и новым пользователям); в каждом письме есть отписка.
2. **Отдельный SMTP для рассылок** настраивается переменными `BULK_EMAIL_*` (пункт меню «SMTP рассылок»).
   Лимит писем в минуту задаётся `BULK_EMAIL_RATE_PER_MINUTE`, по умолчанию
   осторожный — 30 писем в минуту. Без отдельного SMTP e-mail-канал рассылок
   выключен, коды входа идут через основной SMTP как раньше.
3. **Рассылки администратора** уходят по той же аудитории (все, с подпиской,
   просроченные и т. д.) во все три канала; e-mail дополнительно требует согласия
   на новости. Отчёт рассылки в боте читает очередь по `source = broadcast:<id>`
   и показывает по каналам: отправлено, в очереди, ошибки, отменено, не получат.
   Отмена рассылки отменяет и неотправленные копии.
4. **Алерты SMTP** раздельные: «Основной SMTP» (коды входа, напоминания) и
   «SMTP рассылок» — у каждого своё состояние, повтор и сообщение о восстановлении.
5. **Порядок обновления:** сначала Remnashop (новый работает и со старым Clean Pay),
   затем Clean Pay. Меню проверяет это до сборки и предлагает обновить Remnashop.
   Ключи VAPID создаются один раз — при обновлении Remnashop новым меню либо после
   обновления Clean Pay, если Remnashop обновили старым меню.
