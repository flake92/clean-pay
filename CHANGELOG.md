# Журнал изменений

Все заметные изменения Clean Pay документируются в этом файле.

Формат основан на [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/),
версии следуют [Semantic Versioning](https://semver.org/lang/ru/).

## [Unreleased]

## [0.4.0] - 2026-10-22

Обновлённый интерфейс кабинета и страниц входа, тёмная тема и очистка старых
образов в меню. Тексты, формы, маршруты, логика входа и оплаты не меняются.
Миграций нет, формат конфигурации прежний (`CLEAN_PAY_CONFIG_VERSION=0.2.0`);
обновление с `0.2.x` и `0.3.x` — обычное.

### Добавлено

- Тёмная тема: включается автоматически по системной настройке
  (`prefers-color-scheme`).
- Нижняя панель навигации на телефонах («Кабинет», «Друзья», «Тарифы»,
  «Продлить», «Профиль») — те же разделы, что в боковом меню; кнопка чата
  поддержки поднята над ней.
- Кольцевой индикатор трафика вместо полосы, «живой» статус подписки
  (пульсирующая точка, янтарное свечение за 3 дня до окончания), скелетон
  вместо надписи «Загрузка…», конфетти после подтверждённой оплаты.
- Анимации на [Motion](https://github.com/motiondivision/motion) и
  [anime.js](https://github.com/juliangarnier/anime): появление карточек,
  счётчик значений в плитках, наклон плиток за курсором, плавная смена страниц,
  отклик кнопки копирования, анимированный фон кабинета, вибро-отклик кнопок на
  телефонах. При `prefers-reduced-motion` движение отключается полностью.

### Изменено

- Страница входа: анимированный фон, градиентная рамка карточки, градиентные
  кнопки и заголовки. Плитки метрик в кабинете и на странице приглашений —
  круглая иконка рядом с подписью, значение во всю ширину плитки.

### Исправлено

- Утилиты PrimeFlex для цвета текста и фона (`text-500`, `surface-card` и
  другие) ссылались на неопределённые переменные `--p-surface-*` и не
  применялись; палитра определена, классы работают в обеих темах.
- Каждое обновление через `./menu.sh` собирало новую пару образов (~1,4 ГБ) и
  не удаляло прежние, поэтому через несколько обновлений сборка и установка
  останавливались проверкой свободного места. После успешной установки меню
  теперь удаляет образы прежних обновлений с тегом-SHA; текущая версия и та,
  которую она заменила (быстрый откат), остаются. Образы с другими тегами и
  используемые контейнерами не удаляются.

### Безопасность

- Next.js обновлён с 16.3.8 до 16.4.2: исправлены критические уязвимости
  (GHSA-2464-fhr4-w9xw — выполнение кода через Image Optimization с SVG,
  GHSA-673q-mjm6-r5xr — выполнение кода в функциях `use cache`,
  GHSA-p3m5-59mp-jv5r — отказ в обслуживании через Server Actions).
- `vite` закреплён на 8.2.4 (CVE-2026-112942 в 8.2.2, зависимость `vitest`);
  проверка уязвимостей образа снова проходит.

## [0.3.4] - 2026-10-19

Привязка e-mail к аккаунту Telegram. Миграции и формат конфигурации не
меняются (`CLEAN_PAY_CONFIG_VERSION=0.2.0`).

### Исправлено

- Пользователь, вошедший через Telegram, при оплате указывал e-mail, а вместо
  поля для кода видел «Автоматическое объединение аккаунтов остановлено из-за
  конфликта данных» и не мог продолжить. Для нового e-mail создаётся отдельный
  аккаунт Remnashop, и до ввода кода сессия держит его токены; проверка сессии
  при отрисовке страницы принимала это за чужой аккаунт. Теперь страница
  подтверждения e-mail читает данные через ожидающий аккаунт, пока e-mail не
  подтверждён; кабинет и оплата по-прежнему работают только с основным
  аккаунтом, а любой другой аккаунт отклоняется. Пользователям, которые
  застряли на этом шаге, достаточно снова открыть оплату и ввести код из
  письма — объединение аккаунтов пройдёт автоматически.

### Добавлено

- Поддержка панели Remnawave, установленной скриптом eGames (скрыта за
  секретной cookie). Её nginx без cookie отвечает на API `404`, и установка
  останавливалась на «dependencies are not ready: remnawave». Новая
  необязательная переменная `REMNAWAVE_COOKIE` (`ключ=значение`, то же
  значение, что `REMNAWAVE_COOKIE` в `.env` Remnashop) добавляется ко всем
  запросам Clean Pay в API панели и к проверке готовности. Мастер настройки
  спрашивает её после токена Remnawave; значение не выводится на экран.
- В README — пример reverse proxy для nginx, в том числе для nginx в
  Docker-контейнере (`proxy_pass http://clean-pay:4000`).

## [0.3.3] - 2026-10-19

Связь Clean Pay и Remnashop при установке. Код приложения, миграции и формат
конфигурации не меняются (`CLEAN_PAY_CONFIG_VERSION=0.2.0`).

### Исправлено

- Установка останавливалась на проверке совместимости с
  «Remnashop env directory must have mode 700 or 750; actual mode is 755»:
  каталог Remnashop с правами 755 создавали и меню («Установить Remnashop с
  нуля»), и установщик апстрима. Меню теперь само ставит каталогу 750, а `.env`
  — 600 при установке и обновлении Remnashop и Clean Pay.
- После перевода Remnashop с апстрима на сборку Clean Pay в его `.env`
  появлялся новый `APP_AUTH_SERVICE_KEY`, не совпадающий с
  `REMNASHOP_AUTH_SERVICE_KEY` Clean Pay, и установка падала с
  «auth/API contract returned 401 405». Меню теперь после резервной копии и с
  подтверждением переносит ключ Clean Pay в Remnashop и перезапускает API,
  worker и scheduler (при установке и обновлении Clean Pay, при установке и
  обновлении Remnashop). Значения ключей на экран не выводятся.
- Ответ 401 при наличии нового API Remnashop больше не выдаётся за «неверную
  ветку»: проверка пишет, что не совпадает ключ, и называет команду
  исправления. При небезопасных правах `.env` она показывает нужные `chmod`.

### Добавлено

- Пункт меню 11 «Связать с Clean Pay» и команда `./menu.sh remnashop-link`:
  права `.env` Remnashop, общий ключ, перезапуск и проверка совместимости в
  одном действии. Последующие пункты меню сдвинулись на один номер.
- «Установить Clean Pay» в меню выполняет `./deploy.sh configure`, переносит
  ключ и затем `./deploy.sh install` вместо одного `./deploy.sh setup`, поэтому
  ручной паузы на копирование ключа больше нет.

## [0.3.2] - 2026-10-19

Восстановление из резервной копии. Код приложения, миграции и формат
конфигурации не меняются (`CLEAN_PAY_CONFIG_VERSION=0.2.0`).

### Исправлено

- После восстановления базы из дампа (на новом сервере или поверх текущей
  базы командой из пункта «Как восстановить из копии») `./deploy.sh install`
  останавливался на `database-role-provision`: `pg_restore` заново разбирает
  ограничение `_clean_pay_retention_policy_ranges_check`, и PostgreSQL
  «сплющивает» в нём вложенные `AND`. Условие то же, но текст другой — не
  совпадали отпечаток каталога и хэш определения ограничения. Манифест теперь
  содержит отпечатки восстановленной базы для обеих родословных (рабочая база
  и чистая установка) и хэш восстановленного определения; повторное
  восстановление даёт те же значения. Проверено на изолированной копии
  рабочей базы из резервной копии меню для обоих вариантов восстановления:
  проверка ролей, миграции и синхронизация прав проходят, роли приложения и
  воркеров входят, данные на месте.
- «Как восстановить из копии» предупреждает, если код в копии старше 0.3.2, и
  подсказывает, каким кодом выполнять установку.

## [0.3.1] - 2026-10-18

Исправления установки и меню. Код приложения, миграции и формат конфигурации
не меняются (`CLEAN_PAY_CONFIG_VERSION=0.2.0`). Всё ниже проверено на
сервере с 1 vCPU и 2 ГБ памяти.

### Исправлено

- `install` в 0.2.2–0.3.0 останавливался на `database-role-provision` с
  ошибкой «database catalog does not match reviewed
  20260825230000_guard_retention_mutations» на базах, где у индексов
  `PaymentRecord_retentionHoldAt_idx` и
  `PaymentRecord_retention_scrub_candidates_idx` стоит флаг
  `pg_index.indcheckxmin`: в 0.2.2 этот флаг принудительно считался `false`,
  а часть эталонных отпечатков снята с ним. Теперь каталог подходит, если
  проверенному отпечатку соответствует либо его точный снимок, либо снимок со
  сброшенным флагом. Проверено чтением на рабочей базе: 0.2.1 и 0.3.1
  совпадают с эталоном, 0.3.0 — нет.
- «Обновить Remnashop» на установке по compose апстрима snoups (образ
  `ghcr.io/snoups/remnashop`) менял образ, останавливал бота и падал на
  `no such service: remnashop-migration`, оставляя бот остановленным. Теперь
  такая установка определяется заранее и переводится на сборку Clean Pay:
  compose из выбранной версии Remnashop и копия `.env` с недостающими ключами
  (`TASKIQ_DEPLOYMENT_ID`, `REDIS_PASSWORD`, `APP_JWT_SECRET`, `APP_API_KEY`,
  `APP_AUTH_SERVICE_KEY`, `WEB_ENABLED`; прежние значения не меняются)
  проверяются через `docker compose config`, пока старый стек работает, и
  подменяются только после резервной копии. База и Redis остаются в тех же
  томах. Сбой до миграций возвращает прежние compose и `.env` и поднимает
  прежний стек. Compose без сервиса миграций при новых миграциях отклоняется
  до остановки сервисов.
- Ожидание готовности Remnashop больше не ждёт 10 минут проверок здоровья,
  которых нет в compose апстрима: такие контейнеры считаются готовыми после
  минуты работы без перезапусков.

### Требуется Remnashop из `main` форка

- В Remnashop (`flake92/remnashop` `1b982a3`) проверка здоровья taskiq больше
  не загружает приложение: на 1 vCPU она занимала ~5,4 с и при запуске
  превышала таймаут 10 с, worker и scheduler не становились healthy, и меню
  сообщало об ошибке обновления. Теперь ~0,6 с, таймаут — 30 с.

## [0.3.0] - 2026-10-18

Изменения в меню управления `menu.sh`, документации, мастере установки и
тексте ошибки проверки совместимости Remnashop. Код приложения, миграции и
формат конфигурации не меняются (`CLEAN_PAY_CONFIG_VERSION=0.2.0`);
обновление с `0.2.x` — обычное.

### Требования

- Clean Pay и Remnashop работают с **Remnawave 2.8.0** или новее и нодами
  **remnanode 2.8.0** или новее. Требование указано в README, примерах `.env`,
  мастере установки и меню.

### Добавлено

- Пункт меню «Обновить Remnawave» (и `./menu.sh remnawave-update`) для панели
  на этом же сервере. Образ по тегу из compose панели скачивается, пока панель
  работает; версии ниже 2.8.0, смена мажорной версии и откат на более старую
  отклоняются. Затем — обязательная полная копия, подтверждение словом
  `ОБНОВИТЬ`, пересоздание только сервиса backend и ожидание healthy. Если
  новая версия не поднялась, меню возвращает прежний образ. Тег, закреплённый
  на конкретной версии, меню не меняет.
- Версия Remnawave против требуемой 2.8.0 видна в шапке меню, в «Подробном
  состоянии» и в «Проверке сервера» (версия ниже требуемой — ошибка проверки).
- Полная резервная копия включает базу Remnawave, её `.env` и
  `docker-compose.yml`, если панель работает на этом сервере; `manifest.txt`
  содержит версию и образ панели, «Как восстановить из копии» — шаги для неё.
- Настройки меню `REMNAWAVE_CONTAINER` и `REMNAWAVE_DB_CONTAINER`
  (по умолчанию `remnawave` и `remnawave-db`).

### Исправлено

- «Установить Remnashop» и «Обновить Remnashop» больше не предлагают теги
  `v0.x`: в форке это релизы апстрима snoups без интеграции с Clean Pay.
  Операторы выбирали `v0.8.2` (схема Alembic 0040), и установка Clean Pay
  затем падала на проверке совместимости Remnashop. Теперь в подсказке только
  ветки, а выбранная версия до сборки проверяется на ревизию Alembic не ниже
  требуемой (0059) и наличие API `notification-preferences`; несовместимая
  версия отклоняется, ничего не меняя.
- Ошибка проверки совместимости в `deploy.sh` теперь говорит, как её
  исправить: «./menu.sh → Обновить Remnashop → main».

### Изменено

- Нумерация пунктов меню: раздел REMNAWAVE — пункт 11, резервные копии —
  12–14, справка — 15–16.

## [0.2.3] - 2026-10-18

Изменение только в меню управления `menu.sh`. Код приложения, миграции и
формат конфигурации не меняются (`CLEAN_PAY_CONFIG_VERSION=0.2.0`).

### Исправлено

- «Обновить Remnashop» теперь переносит в существующий compose проверки
  здоровья (healthcheck) из устанавливаемой версии Remnashop. Раньше менялся
  только образ, и уже установленный Remnashop продолжал запускать тяжёлые
  проверки каждые 30 секунд — на сервере с 2 vCPU это давало скачки CPU до
  50–80 %. Переносятся только параметры проверок `web` и `taskiq`
  (`interval`, `timeout`, `retries`, `start_period`, `start_interval`),
  остальной compose не меняется; изменение проходит ту же проверку
  `docker compose config` с возвратом прежнего файла при ошибке. На Docker
  Engine старше 25 `start_interval` не переносится.

## [0.2.2] - 2026-10-17

Исправления пути обновления с 0.1.x. Новых миграций БД нет, формат
конфигурации прежний (`CLEAN_PAY_CONFIG_VERSION=0.2.0`). Установкам на 0.2.x
обновляться не обязательно: поведение работающего приложения не меняется.

### Исправлено

- `./deploy.sh prepare-v0.1.1-upgrade` (и `sh start.sh prepare-v0.1.1-upgrade`)
  всегда завершались ошибкой `production operation name is invalid`: имя
  команды с точками передавалось в блокировку производственных операций,
  которая принимает только `[a-z0-9-]`. Теперь команда берёт блокировку под
  именем `prepare-v011-upgrade`; проверка имён не ослаблена. Обход через
  `node-tooling.sh operation-lock acquire` больше не нужен.
- `database-role-provision` останавливал `install` после миграций
  `20260825*` на базах с реальными данными: индексы
  `PaymentRecord_retentionHoldAt_idx` и
  `PaymentRecord_retention_scrub_candidates_idx` строятся в той же
  транзакции, что и заполнение `PaymentRecord`, и PostgreSQL ставит им
  `pg_index.indcheckxmin`. Этот служебный флаг входил в отпечаток каталога.
  Теперь он в отпечатке не учитывается (фиксируется как `false`, с этим
  значением сняты все эталоны). Ручной `VACUUM`/`REINDEX` перед `install`
  больше не нужен.
- Журналы миграций, созданные официальным v0.1.0 (`47aadf6`), не проходили
  проверку контрольных сумм: в этом релизе миграции
  `20260619153000_add_auth_cache_models` и `20260619154500_add_telegram_oidc`
  лежали со смешанными концами строк CRLF/LF. Их суммы добавлены в
  проверенный список; после приведения концов строк файлы байт в байт
  совпадают с текущими.

## [0.2.1] - 2026-10-16

Обновление в пределах 0.2.x: новых миграций БД нет, формат конфигурации
прежний (`CLEAN_PAY_CONFIG_VERSION=0.2.0`). Установкам, где кабинет открывается
по двум доменам, перед сборкой нужно задать `NEXT_PUBLIC_APP_ALIAS_ORIGINS`
(см. «Изменено»).

### Безопасность

- Анонимный вход, регистрация и сброс пароля получили лимит на IP клиента
  (100 за 15 минут) перед общим лимитом `AUTH_RATE_LIMIT_CAPACITY`. Раньше
  один источник без капчи мог исчерпать общий лимит и заблокировать вход для
  всех пользователей до конца окна. Тот же принцип применён к проверке
  passkey при входе: её собственный лимит раньше игнорировался.
- Лимит на ввод кода подтверждения e-mail считается по пользователю, а не
  только по присланному клиентом адресу: меняя адрес, можно было обходить
  ограничение на подбор кода.
- Проверка пароля при привязке e-mail к аккаунту расходует тот же лимит, что
  и вход (5 попыток за 15 минут), и больше не служит вторым способом подбора
  пароля.
- Активация промокода ограничена 10 попытками за 15 минут на пользователя.
- Расшифровка AES-GCM требует полный 16-байтовый тег аутентификации.
- Удалён неиспользуемый уровень сессии `BOOTSTRAP` вместе с путём, на котором
  регистрация passkey повышала такую сессию до полной без проверки e-mail.
  Сессии и токены с уровнем, отличным от `FULL`, отклоняются везде.

- Production-зависимости снова без известных уязвимостей уровня high:
  `sharp` 0.35.5 (уязвимость librsvg) и `source-map-js` 1.2.2 (DoS через
  индексированные source maps). Исправлено повреждённое значение override
  `fast-uri`.
- Базовый образ Node.js обновлён с 24.18.0 до 24.22.0 (Debian 12.15), а
  runtime-образ применяет вышедшие обновления bookworm-security: в нём больше
  нет семи исправленных уязвимостей `perl-base`.
- Исключения сканера образов, истёкшие 30 сентября, пересмотрены: оставлены
  только находки без исправления в Debian, добавлены три новые с обоснованием,
  срок действия — до 30 ноября 2026 года.
- Репетиция отката образа в CI снова выполнима: базовым коммитом стал
  `6bfa135` — тот же релиз, что исторический `0ede176`, но из переписанной
  истории `main` (runtime-код идентичен). Для него действует та же проверенная
  проекция окружения отката.

### Добавлено

- Необязательная переменная `NEXT_PUBLIC_APP_ALIAS_ORIGINS`: дополнительные
  HTTPS-адреса той же установки (второй домен). Значение вшивается в образ и
  одинаково используется защитой от CSRF и проверкой Server Actions в Next.js;
  валидатор окружения требует пересборки, если оно расходится с образом.
  Workflow публикации образов принимает его параметром `app_alias_origins`.
- Раздел «Переменные окружения» в README с описанием всех настроек;
  `deploy/prod/.env.example` дополнен недостающими переменными.
- Интерактивное меню управления `./menu.sh`: состояние и проверка сервера,
  логи, установка и обновление Clean Pay через проверенные этапы `deploy.sh`,
  обновление и установка Remnashop с явным запуском миграций Alembic,
  резервные копии с проверкой и готовые команды восстановления. Перед каждым
  глобальным действием меню делает полную проверенную резервную копию (базы

  неудачный запуск без новых миграций возвращают предыдущую версию
  автоматически. Те же операции доступны командами `./menu.sh status`,
  `backup`, `verify`, `update` и другими.

### Изменено

- Публичные домены конкретной установки больше не прописаны в коде. Если
  кабинет работает на двух доменах (например, `pay.example.com` и
  `pay2.example.com`), второй нужно указать в
  `NEXT_PUBLIC_APP_ALIAS_ORIGINS` и пересобрать образ, иначе вход и оплата на
  нём будут отклонены защитой от CSRF.
- Действия авторизованного пользователя (покупка и продление, смена пароля и
  e-mail, подтверждение e-mail, привязка и объединение аккаунтов, настройки
  напоминаний) ограничиваются только по самому пользователю. Общий лимит
  `AUTH_RATE_LIMIT_CAPACITY` действует лишь для анонимных попыток входа.
- Обновление статуса оплаты обращается к Remnashop не чаще 120 раз за
  5 минут на пользователя; сверх этого показывается сохранённый статус.
- Настройка passkey всегда необязательна.

### Исправлено

- Общий лимит на действие (1000 за 15 минут на весь сервис) раньше
  распространялся и на оплату: при большом числе покупщиков checkout
  останавливался для всех.
- Сравнение идентификатора платежа на странице статуса не зависит от регистра.
- Снапшот-тесты JSX не зависят от отступов исходника.
- Вход через Telegram Mini App для пользователя, чей аккаунт Remnashop был
  объединён с Telegram-аккаунтом (сначала регистрация по e-mail, затем привязка
  Telegram). Сверка личности возвращает ветку восстановления без токенов
  провайдера, а вход требовал их заранее и всегда завершался ошибкой «Не удалось
  войти через Telegram». Теперь, как и в OIDC callback, сессия создаётся без
  токенов, а восстановление получает токены подтверждённого владельца.
- Отказ входа через Telegram Mini App пишется в технический журнал
  (`telegram_webapp_login_failed` с кодом ошибки): раньше он не оставлял следов.
- Кнопка «Повторить вход через Telegram» на экране ошибки Mini App и
  автоматический переход при отсутствии данных Mini App вели прямо на
  `/auth/telegram/start` без токена Cloudflare Turnstile и при включённом
  Turnstile всегда получали отказ (403). Теперь повтор заново запускает вход
  Mini App, а без данных Mini App пользователь попадает на страницу входа, где
  Turnstile пройден штатно.

### Добавлено для пользователей

- Для Telegram-пользователя добавлен управляемый сценарий подготовки аккаунта к оплате:
  проверка подтверждённого e-mail выполняется до показа checkout, а выбранные тариф,
  длительность и платёжный шлюз сохраняются при переходах через привязку аккаунта,
  подтверждение e-mail и настройку Passkey.
- Тариф может предлагать несколько платёжных шлюзов. Выбор шлюза отделён от выбора
  длительности и не смешивает предложения при переходах назад и вперёд.
- На страницах тарифов поддержан перенос длинных описаний на узких экранах.

### Исправлено и уточнено для пользователей

- Корневой URL направляет анонимного пользователя на вход, а пользователя с действующей
  сессией — в кабинет. Кабинет, профиль и страницы статуса платежа корректно отправляют
  на вход после истечения сессии и сохраняют безопасный адрес возврата.
- Устранены гонки создания и восстановления сессии: новый auth-cookie не затирается,
  кабинет восстанавливается после параллельной авторизации, повторный callback не меняет
  уже подтверждённого владельца аккаунта.
- Восстановлена двусторонняя привязка e-mail и Telegram, усилена обработка конфликтов
  merge и сохранение Telegram-идентичности целевого аккаунта.
- Подтверждение и смена e-mail теперь показывают ошибку рядом с нужной формой, учитывают
  cooldown/rate limit и не расходуют лимит до проверки конфликта владельца.
- Смена пароля не является новой функцией 0.1.1 — она уже была в 0.1.0. В этой версии
  операция перенесена в Server Action, ограничена пятью попытками за 15 минут, отклоняет
  пароль короче восьми символов и совпадение со старым паролем, обновляет локальную
  сессию только после ответа Remnashop и записывает аудит пользователя.
- Для Passkey используется platform authenticator; регистрация, удаление и вход проверяют
  владельца challenge, authenticator counter и подтверждённость аккаунта до полной сессии.
- Статус успешного локального платежа сохраняется при временном сбое обновления Remnashop;
  страницы возврата продолжают опрос с backoff до терминального состояния и не теряют
  выбранную операцию.
- Новые условия продления требуют повторного подтверждения цены; внутренние ошибки
  провайдера не показываются пользователю.
- Промокод можно активировать без текущей подписки; исправлены повторный выпуск ссылки,
  сброс устаревшего сообщения после закрытия PWA-установки и действия профиля.
- Сведения об устройствах показывают нормализованные платформу, ОС и клиент без HWID,
  raw User-Agent и управляющих Unicode-символов; удаление остаётся привязано к исходному HWID.
- Анонимное верхнее меню больше не показывает действия кабинета. Иконочные кнопки получили
  `aria-label`, `aria-expanded` и `aria-controls` для клавиатуры и screen reader.

### Платежи и целостность данных

- Идемпотентность и reconciliation уже присутствовали в 0.1.0. В 0.1.1 усилен порядок
  `create → claim → authorize → dispatch → settle`: смена пользователя до отправки
  блокируется, изменение предложения фиксируется до вызова провайдера, а неизвестный
  результат после отправки остаётся `pending` и не создаёт повторный платёж.
- Синхронизация статуса сначала использует точный `payment_id`, затем ограниченную историю;
  для старого Remnashop сохранён fallback на legacy transactions contract.
- Повтор reconciliation защищён владельцем и lease, спорные результаты переводятся в
  `manual_required`, а ошибка необязательного аудита не понижает уже подтверждённый платёж.
- После merge владелец истории и операций переносится согласованно; конфликт чужого
  `payment_id` или изменившаяся подписка завершают операцию безопасной ошибкой.
- Добавлена единственная новая миграция
  `20260810013000_preserve_account_merge_target_telegram`: nullable-поле
  `AccountMergeConfirmation.targetTelegramId` сохраняет Telegram-владельца, зафиксированного
  на этапе подготовки merge. Содержимое старых миграций не изменилось, кроме нормализации EOL.

### Авторизация и безопасность

- Ротация refresh token выполняется атомарно: параллельные запросы получают одного successor,
  повтор в grace window возвращает его же, поздний reuse отзывает только затронутое семейство.
- Logout всегда удаляет cookies, даже если PostgreSQL недоступен; отозванная сессия очищает
  зашифрованные access/refresh-токены Remnashop, а аудит получает `userId` из проверенного cookie.
- При смене/сбросе пароля старые локальные сессии и upstream-токены отзываются fail-closed;
  ошибка cleanup не оставляет браузер с действующими cookies.
- Одноразовые состояния, Telegram callback/WebApp, Turnstile, CSRF и rate limiting получили
  проверки владельца, действия и срока; чувствительные значения сравниваются constant-time.
- Статический CSP заменён на nonce-based CSP со `strict-dynamic`; включены годовой HSTS,
  WebAuthn в `Permissions-Policy` и явная модель доверенных proxy hops через
  `TRUSTED_PROXY_HOPS`.
- Turnstile site key для frontend-сборки отделён от runtime secret. Логи редактируют секреты
  и персональные данные, а request/trace ID передаются между внутренними вызовами.
- Зависимости обновлены до Next.js `16.3.0`, React `19.2.8`, Prisma `7.9.1` и Vitest
  `4.1.10`; overrides закрывают известные уязвимые транзитивные версии.

### Наблюдаемость и эксплуатация

- Добавлен защищённый `GET /api/internal/metrics`. Он требует
  `X-Clean-Pay-Readiness-Secret` и отдаёт Prometheus text format `0.0.4`: readiness gauge,
  backlog/возраст/попытки reconciliation, счётчики operational events, upstream-запросов
  и их длительность. Prometheus server в Compose не устанавливается — подключается внешний scraper.
- Labels upstream-метрик нормализуют UUID, числовые ID, e-mail/Telegram identity и query string,
  чтобы не публиковать секреты и не создавать неограниченную кардинальность.
- Подробный readiness остаётся защищённым, публичный endpoint отдаёт только кэшированный
  статус. Проверяются PostgreSQL, Redis, публичный и auth-контракты Remnashop, Telegram OIDC,
  а при настройке — Mailpit и Remnawave; тела HTTP-ответов закрываются после проверки.
- `reconciliation-worker` и `retention-worker` записывают heartbeat только после успешного
  цикла. Compose помечает контейнер unhealthy, если heartbeat отсутствует или устарел.
- Для app установлен лимит Docker `json-file` в три файла по 10 МБ; для worker и
  инфраструктурных контейнеров — два файла по 5 МБ. Debug override увеличивает лимиты явно.

### Развёртывание

- `./deploy.sh` без аргументов запускает интерактивный мастер из трёх этапов:
  заполнение `deploy/prod/.env`, проверка готового Compose и установка с миграциями,
  readiness/HTTPS/security-header проверками и понятной диагностикой.
- Node.js закреплён на `24.18.0` в Docker, `.node-version` и `.nvmrc`; pnpm workspace и
  lockfile удалены, Prisma Client генерируется одинаково перед dev/build/test.
- Единый multi-stage `Dockerfile` создаёт отдельные migration и standalone runtime images.
  Приложение и worker стартуют только после успешного `prisma migrate deploy`.
- Перед Docker build проверяется минимум 8192 МБ свободного диска. Автоочистка затрагивает
  только неиспользуемые Docker-артефакты и повторно проверяет свободное место.
- Установщик проверяет auth/payment endpoints, service key и минимальную Alembic revision
  Remnashop; legacy payment rollout gate снимается только после всех проверок и повторно
  проверяется после изменения.
- README переписан как инструкция владельца: первичная установка, ежедневные команды,
  обновление, восстановление и диагностика без сведений о частном тестовом стенде.

### Архитектура, HTTP-контракты и CI

- Внутренние браузерные `/api/bff/*`, `/api/me` и `/api/logout` из 0.1.0 удалены. Это не
  поддерживаемые внешние API: эквивалентные пользовательские сценарии работают через Server
  Components и Server Actions. Внешними HTTP-контрактами остаются health/readiness, metrics,
  reconciliation и Telegram callbacks, перечисленные в `src/app/api/ENDPOINTS.md`.
- Domain/application/infrastructure/presentation разделены автоматическими architecture-тестами;
  persistence и внешние SDK изолированы в adapters, а application-слой владеет порядком use case.
- CI запускает lint, строгий typecheck, unit/route/integration/PostgreSQL concurrency тесты,
  полный Docker E2E, secret scan, CodeQL, SBOM и Trivy production image.
- Релизная проверка: 118 test files и 903 теста прошли; production build успешен;
  `npm audit` не нашёл известных уязвимостей; CI для `main` и `v0.1.1` завершён успешно.

### Обновление с 0.1.0

- Сделайте резервную копию `deploy/prod/.env` и PostgreSQL перед обновлением production.
- Сверьте `.env` с `deploy/prod/.env.example`. Новые параметры: `CLEAN_PAY_MIN_FREE_DISK_MB`,
  `REMNASHOP_AUTH_SERVICE_KEY`, контейнеры и минимальная Alembic revision Remnashop,
  `TRUSTED_PROXY_HOPS`, `AUTH_RATE_LIMIT_CAPACITY` и `AUTH_CONCURRENCY_LIMIT`.
- Одинаковый `REMNASHOP_AUTH_SERVICE_KEY` должен быть задан в Clean Pay и Remnashop;
  используйте совместимую версию auth/payment contracts, указанную в README.
- Для локальной разработки используйте Node.js из `.node-version`. На production Node.js
  устанавливать не нужно: runtime и migration CLI находятся в разных Docker stages.
- Применяйте только `prisma migrate deploy`. Штатный `./deploy.sh install` выполняет новую
  additive-миграцию, ждёт healthcheck и не удаляет Docker volumes.
- Если внешняя интеграция неофициально вызывала `/api/bff/*`, её нужно перевести на
  поддерживаемые внешние controllers; браузерные BFF-контракты больше не существуют.
