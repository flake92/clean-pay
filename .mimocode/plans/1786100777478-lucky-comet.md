# Рефакторинг payments/history-sync.ts

## Контекст
Продолжаем Фазу 4 рефакторинга. Файлы `idempotency.ts` и `reconciliation.ts` завершены. Следующий — `payments/history-sync.ts`.

## Анализ

### Транзакционные вызовы (3 блока) — оставляем как есть
| Функция | Строка | Причина |
|---------|--------|---------|
| `claimPaymentHistorySync` | 80 | `FOR KEY SHARE` + `FOR UPDATE` + conditional claim |
| `completePaymentHistoryPage` | 260 | Lock + verify + apply + advance |
| `failPaymentHistorySync` | 343 | Read-then-conditional-release + audit |

### Простые вызовы (2 штуки) — НЕ рефакторим
| Функция | Строка | Вызов | Причина отказа |
|---------|--------|-------|----------------|
| `loadCurrentPaymentHistoryCredential` | 419 | `prisma.$queryRaw` | Raw SQL с `CROSS JOIN LATERAL`, `FOR KEY SHARE`, `clock_timestamp()` — не маппится на типизированный API |
| `continuePaymentHistoryBackfills` | 512 | `prisma.$queryRaw` | Raw SQL с `INTERVAL`, `EXISTS`, `clock_timestamp()` — не маппится на типизированный API |

## Решение
**Пропускаем этот файл.** Все 5 вызовов prisma либо транзакционные, либо используют PostgreSQL-специфичные конструкции, которые не маппятся на существующие сервисные интерфейсы. Создание нового `PaymentHistorySyncStateStore` с транзакционными методами не даёт выигрыша в абстракции.
